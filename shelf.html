Before you sit down

Get started

Four things that have to be true before the first exercise. None of them takes more than five minutes, and the fallback is on the list because a stalled account is the most common way to lose a morning.

  1. Codex, open and signed inCheck it the night before, not at ten. Start a fresh chat after installing anything.
  2. One project, a few foldersAdd only what it needs to read — the build, your exported assets, a reference archive. Never a whole drive.
  3. One screen you ownAn export, a screenshot or a Figma link. Your own work moves the result off the generic baseline faster than any prompt.
  4. A starter brief in reservePrinted, at the door. Take it the moment a login, an account or a download stops you.

One folder, one file

Start with HTML

Make an HTML folder and prototype everything in it. Not because HTML is the final answer, but because it is the shortest distance between an idea and something you can look at. There is no install, no build, no framework to satisfy first — you write a file, you open it, you see it. That gap is where most ideas die, and HTML removes it.

  • Websites

    A landing page is a file. Open it, change a line, reload — no build step between the idea and the thing.

  • Typography

    Set a scale, try a pairing, print a specimen. The browser is already the best type renderer you own.

  • Page sections

    Build one section at a time and keep the ones that work. A section is small enough to throw away.

  • Books

    Pages, spreads, running heads, a bound reader. This codex is one file.

  • Motion

    Keyframes, easing, scroll-driven timelines — and frames you can record straight off the canvas.

  • Articles

    Long-form with real columns, drop caps and footnotes, laid out where it will actually be read.

One file travels. Drag it into a message, a folder, a deck, someone else’s machine — there is no node_modules to bring with it, which is not true of a React project. It is also the most hospitable format there is: drop in Three.js for real 3‑D, a canvas for a shader, a video element, a web font. And nothing here is a dead end — whatever survives as HTML can be lifted into whatever framework or platform it needs to live in afterwards.

Faster than typing, and looser

Use your voice

You think faster than you type, and a spoken brief carries more of the situation than a typed one — the aside, the caveat, the thing you would not have bothered to write. That is the whole argument. It also frees your hands, which is what makes running two or three threads at once bearable.

  • Wispr FlowDictation, everywhere

    Speak into any field on the machine and get clean text out. The one that turns a brief you would not have typed into one you did.

    wisprflow.ai
  • SuperwhisperVoice to text, offline

    The same job on macOS, Windows and iOS, with models that can run locally when the work should not leave the machine.

Tells, and what to do instead

How to avoid AI slop

Every wave of generated interfaces converges on the same look, and the look moves. These are the tells that survive a model change, drawn from Meng’s own breakdown and from Impeccable’s catalogue of sixty-four patterns. None of them is forbidden. Each is a default — something the machine reaches for when nobody made a decision. The fix is always the same shape: make the decision yourself, and be able to say why.

  • Purple gradients

    Violet-to-blue on everything — buttons, headings, orbs. The single most recognisable palette in generated work.

    Pick a palette on purpose, from something real.
  • Glow and glass

    Blurred orbs, frosted cards, neon rims on dark. Decoration standing in for a lighting decision.

    Light the composition with material, or leave the surface plain.
  • The tracked eyebrow

    A tiny letter-spaced label sitting above an oversized headline. It borrows editorial authority it has not earned.

    Fold the kicker into the headline, or drop it.
  • The decorative grid

    Graph-paper ruling behind a section that is not a canvas, a map or anything being measured.

    Use the product’s own structure, or a plain field.
  • One font for everything

    Inter, Geist, Space Grotesk — the same handful of faces, used for headings, body and labels alike.

    Pair a display face with a body face. Let them differ.
  • The side-tab card

    A thick coloured bar down one edge of a rounded card, fighting the corner radius it sits inside.

    Remove the bar, or remove the radius. Not both at once.
  • The icon tile

    A small rounded square with an icon in it, stacked above a heading. Every generator outputs this exact shape.

    Set the icon beside the heading, or let it sit in flow.
  • Generic illustration

    A faceless blob figure that could belong to any product, introducing something specific.

    Show the actual thing. No picture beats a stock one.

A list is not taste, and this page would fail parts of it: Impeccable flags a warm cream ground as a tell in its own right, and this whole codex is one. The difference is whether it was chosen. Run impeccable.style/slop over your build to see which rules fire, watch the breakdown for the workflow around it, then argue with both.

Written, not improvised

Prompt examples

Each of these belongs to a sitting on the shelf. They are short because the evidence does the work: a prompt that has to describe its reference in adjectives is a prompt with no reference attached to it.

  1. Chapter II · Mobbin and inspiration Describe this reference in three terms only — flow, form and voice. Then say what I should borrow from it and what has to change.
  2. Chapter II · The best prompt for a reference Use [A] for the flow and [B] for the visual rhythm. Rebuild it for [my audience and story]. Change [one defining rule]. Keep it to one self-contained file.
  3. Chapter III · Start prompting Keep the mechanism from this reference. Change the content, the scene and the visual direction until only the structure is borrowed — then tell me what stayed and what changed.
  4. Chapter III · Refine and feedback Give me two versions of this section that differ in exactly one thing: [type / colour / density]. Hold the content and the mechanism still.
  5. Chapter II · Typography, colour, layout Read the study and write design.md in four parts — type, colour, spacing and a small component vocabulary. Add a line to AGENTS.md telling you to read it before any change to the interface.

V
Write a super prompt

Any reference · a directive you can still edit

Hand over the reference — an image, a video, a page, a paragraph — and ask for a prompt back rather than a build. What returns is one very long directive that names structure, type, colour, spacing, imagery, motion and tone. Code is the other way to carry a reference and it is far more prescriptive: to change it you edit the thing itself. A super prompt is prose, so you can argue with it, cut a clause, swap a rule, and run it again. Point it at design.md and it inherits your system instead of the reference’s.

  1. Analyse the attached reference and write me a super prompt that could rebuild it from nothing. Cover structure, type scale, colour, spacing, imagery, motion and tone. Describe it in prose. Do not write code.
  2. Watch the video first. Describe the motion as state, trigger, duration and response, then fold that in as a behaviour section of the prompt.
  3. Rewrite the super prompt so it obeys design.md. Where the reference conflicts with my system, keep my system and tell me what you dropped.
  4. Give me the same super prompt with one variable changed: [density / typography / colour logic]. Keep every other clause word for word.

What the prompt has to name before it is detailed enough

  • Structure and layout
  • Type scale and pairing
  • Colour and contrast
  • Spacing and density
  • Imagery and treatment
  • State, trigger, duration
  • Tone of voice
  • What may change
  • What must not

Combined workshop versionAnalyse the attached reference and return one super prompt, not a build. Cover structure, type scale, colour, spacing, imagery, motion and tone, in that order, in prose. Obey design.md wherever it conflicts with the reference. Finish with two lists: the clauses I may change, and the ones that must stay for it to still work.

VI
Run it on a schedule

Automations · the work that repeats without you

A prompt you run once is a task. A prompt on a timer is a colleague. The two that earn their keep are the jobs nobody wants to do every morning: reaching the people who just arrived, and walking the whole product to check it still works. Give it a cadence, a scope and a definition of done — an automation with a vague finish line will report success forever. And decide whether it may act or only draft: anything that sends should show you the list first.

  1. Every 24 hours: find everyone who started a paid subscription in the last day and draft each of them an email inviting them to the Slack channel. Skip anyone already invited. Show me the list before anything sends.
  2. Every 24 hours: walk the site page by page — sign-up, log-in, purchase, browse, courses, tutorials. Check each page loads, each form submits and each link resolves. Report only what broke, with the URL and the step it failed on.
  3. Every hour: check the build is green and the site is up. Say nothing unless something changed.
  4. Every week: one page on what shipped, what broke and what is still open. No adjectives.

Settle these before you leave it running

  • Every hour
  • Every 24 hours
  • Every week
  • Scope: which pages
  • Scope: which people
  • A definition of done
  • What counts as failure
  • Where it reports
  • Draft, or send

Combined workshop versionEvery 24 hours, walk the site page by page — sign-up, log-in, purchase, browse, courses, tutorials — and confirm each one loads, submits and resolves. Then find everyone who subscribed in the last day and draft their Slack invitation. Report only what broke, and show me the drafts before anything is sent.

VII
Send it to another thread

Threads · work that runs beside you

The cost of one long conversation is that everything queues behind whatever it is doing. Opening a fresh task is not the fix — a fresh task starts blind, and you pay for all the context again. Ask the thread you are already in to open another one and hand it what has been settled. The difference between a thread and a sub-agent is who is watching: a sub-agent is something the agent spins up and reconciles on its own, and a thread is one you can open, read and steer. Both exist; only one of them is yours to follow.

  1. Do this in a new thread and keep working here: [task]. Carry over design.md and the direction we already settled.
  2. Open one thread per section — hero, pricing, footer. Same system, same reference. Tell me when each comes back.
  3. That job is long. Put it on its own thread so this one stays free, and come back when it needs a decision from me.
  4. Summarise what this thread has settled in ten lines, then start a fresh thread from that summary.

Hand the new thread these, or it starts blind

  • The decision already made
  • design.md
  • The reference
  • What done looks like
  • What it must not touch
  • Where to report back
  • Watch it, or let it run

Combined workshop versionTake the pricing section on its own thread. Carry over design.md, the reference and the direction we settled here. Do not touch the header or the footer. Come back with a diff and the one thing you were unsure about.

VIII
Drive the screen yourself

Browser and computer use · the fallback that always works

This is the one that removes “there is no integration for that” as a reason not to automate something. No MCP for the service, no CLI either, the thing lives on your own machine, or the only way in is a login — the agent can drive the screen the way you would. Test the site as a new customer, sign in, read the inbox, watch it render. Two habits keep it useful rather than frightening: say plainly whether it may act or only look, and keep anything that speaks in your name as a draft. Research is work you can hand over; posting under your own name is not, and comments written to pass as organic are the fastest way to lose an account and a reputation at once.

  1. Open [site] in the browser, sign in, and list every unread private message with who sent it and what they want. Reply to nothing.
  2. Draft a reply to each of those in my voice — short, direct, no filler. Show me all of them together; I will send them myself.
  3. Search Reddit for threads where people describe the problem my product solves. Give me the ten most relevant with one line on why each fits. Post nothing.
  4. Walk sign-up, log-in and purchase in the browser as a new user would. Screenshot every step and tell me the first place it broke.

Reach for it when

  • No MCP for it
  • No CLI either
  • It lives on your machine
  • The way in is a login
  • You need to see it render
  • The proof is a screenshot
  • Read only, or may act
  • Drafts, never sends

Combined workshop versionOpen the site in the browser, sign in as me, and walk sign-up, log-in and purchase the way a new customer would. Screenshot each step and tell me the first thing that broke. Then list every unread message with a drafted reply underneath it. Send nothing and post nothing — I will review the drafts.

IX
Let it run in a loop

Agent loops · a goal it can score itself against

/grill-me ↗
/wayfinder ↗

A loop needs two things: a goal the agent can test itself against, and permission to keep going without you. Which makes the goal the whole job, and that is why this starts before any agent runs — Matt Pocock’s /grill-me is a relentless interview that takes a loose idea and asks in rounds until you can commit to it. It writes nothing; it just leaves the idea sharp enough to hand over. Self-verify until perfect is then the cheapest loop there is, and it already works. Past that you can have agents check other agents’ work, or reach for /wayfinder, which puts the plan on a tracker so the loop survives the session that started it. But the harnesses now run long on their own: give Opus 5 a goal and it will work for hours. So the job has shifted. It is less about orchestrating rounds and more about handing it something it can keep score against — a video, a whole project, a reference dense enough to check every pass without asking you. Complexity sets the runtime: the harder the thing, the longer it will sit there, and that is the point rather than a problem.

  1. [goal]. Self-verify until it matches the reference. Do not stop to ask me.
  2. Here is the goal and the reference video. Work until the result matches it, frame for frame. Report only when you cannot get closer.
  3. Write the checks you will run before you start. Then loop until every one of them passes.
  4. Run three passes at this independently, then a fourth agent to score them against the goal and keep the winner.

What a loop needs before you walk away

  • A goal worth the hours
  • A goal it can test
  • A reference to score against
  • Checks written first
  • What done means
  • A budget, or a stop
  • Leave to keep going
  • Where it reports
  • When to fetch you

Combined workshop versionHere is the goal and the reference. Write the checks you will run first, then work until every one passes. Score each pass against the reference, not against your own last attempt. Do not ask me between rounds — come back when it is done, or when you are stuck and can say why.

X
Turn it into a skill

The step people skip · a prompt that outlives its thread

MengTo/Skills ↗

A prompt is not an asset. It lives in one thread and dies with it, and the next time you want it you retype it slightly worse. A skill is the same thing written down where the agent can reach it by name, from any project, as a slash command. The moment to write one is when you are happy — a sequence of steps that worked, a workflow you would repeat, a house style you keep describing from scratch. Hand over the thread and let the skill creator ask you the four things that matter. Chapter I set the threshold at the third time you type it; this is what you do when you hit it. And then the step almost everybody skips: push it up. A skill in your own folder saves you an afternoon. A skill in public is a reason for people to know who you are.

  1. We just did something worth keeping. Turn it into a skill: when to use it, what to provide, the steps, and how to check the result.
  2. Read this thread and write the skill from what actually worked, not from what I asked for first.
  3. Name the trigger so you would reach for this on your own next time. Show me the trigger line and nothing else.
  4. Push it to a public repo with a README that shows one before and one after.

A skill worth keeping names all of these

  • When to use it
  • What to provide
  • The steps
  • How to check the result
  • A trigger you would recognise
  • One worked example
  • When not to use it
  • Yours, or public

Combined workshop versionTurn what we just did into a skill. Write when to use it, what to provide, the steps, and how to check the result. Name the trigger so you would reach for it yourself next time. Show me the whole thing as one file — and tell me the one case where it should not be used.
